# Table QR ordering

Admin: `/admin/tables` (admin access required). Create the actual table label, then download or print its QR code. No physical tables are seeded or guessed.

Generate customer QR codes on the deployed frontend. Codes generated at localhost point to localhost and cannot be used from another customer's phone. Deploy both updated frontend and backend before using production codes. No new environment variables are required.

## Customer and staff flow

1. Scan `/table/<random-code>` and check the displayed table label against the physical table.
2. Select Browse menu & order here. The active table appears on menu, cart, and checkout and survives refresh in that tab. Existing cart state and item types are reused.
3. Add dishes, open the cart and proceed to checkout. Dine-in checkout requires name, email, Saudi mobile and the existing Clerk sign-in. Delivery/pickup details and fees do not apply. Tax and item pricing are calculated by the existing backend.
4. Continue to the existing Stripe checkout. An unpaid order cannot enter the kitchen. Only the signed payment webhook marks payment verified.
5. Cashier reviews payment and table, then accepts the order. Kitchen sees the saved table label, starts preparation and finishes preparation.
6. The order becomes `ready_for_table`. Staff physically serve the food; cashier chooses Serve to table and confirms. The order becomes completed with the normal audit trail.

Use Leave table ordering to return to delivery/pickup checkout. Each diner signs in and creates their own order; shared table billing, waiter assignment, and pay-after-eating are not implemented.

## Administration and security

- Table labels are unique. Public QR resolution reveals only label and availability, not other diners' orders.
- Random 192-bit codes are generated by the backend. Browser-supplied table labels/IDs are rejected in checkout; only a valid enabled QR code is resolved into the saved table snapshot.
- Disable a table to block new orders/payment sessions. Replace QR code to revoke the old link, then reprint the sign. Existing paid orders retain the original label for audit and can still be served.
- Label edits and code replacement require the latest updatedAt, preventing stale overwrites.
- A static QR can be photographed or shared; it does not prove physical presence. Cashier must confirm the actual table before acceptance.
- Dine-in uses the confirmed restaurant hours and pickup preparation estimate; it does not require delivery coverage or a delivery driver. Online ordering and Stripe readiness checks remain enforced.

## Checks

`npm run --prefix server test:flow` includes isolated MongoDB table lifecycle, permissions, forged/invalid/disabled code rejection, server prices, payment ownership, signed Stripe payment event, kitchen privacy and preparation, role checks, and table serving. It deletes its isolated test database; it does not mutate restaurant orders or charge a card.

`npm run --prefix client test:tables` tests admin QR creation, actual image decoding, responsive layouts, table/cart persistence, phone validation, Stripe redirect fixture, cashier/kitchen/served screens and disabled QR state. `test:flow` checks the existing delivery and storefront browser flow.

These checks use payment/auth fixtures. After deployment, perform a Stripe test-mode purchase from a real phone and verify the signed webhook, physical table QR and staff handoff before taking customer payments.
